## 1. 長期ゴール（北極星）

**きれいに組版された楽譜のページ画像を、ローカルだけで、数秒で、正しい `.lys` テキストに変換する。**

- クラウドの AI は使わない。最終形は「楽譜読み取りに特化した小さなローカルモデル」と、
  記譜の規則による検証との組み合わせ。
- 対象は商用品質の浄書（LilyPond、MuseScore、Finale/Sibelius/Dorico 系）。手書きは対象外。
- 正しさの基準は「Lily# で描き直すと元の楽譜と同じになる」こと。

## 2. 設計の原則

1. **正解は Lily# に作らせる。** 生成した `.lys` を lysc で PNG と SVG に描き、SVG のグリフと
   `data-pos` を記号単位の正解にする。手で正解を作るのは実譜のベンチマークだけ。
2. **閾値を足す前に、構造（記譜の制約）を探す。** 例: 和音は符幹を共有する、付点は和音単位、
   小節の長さは拍子と一致する。閾値の微調整は最後の手段にする。
3. **形は学習し、位置関係は規則で書く。** 分類器が「何の形か」を決め、規則が「どこにあれば何か」を
   決める。分類器に自信がないときは、規則にフォールバックする。
   **新しい刷りへの対応は、画像処理の規則を足す前に、劣化の種類を足して検出器を学習し直せないかを先に考える**
   （2026-10-26、他の OMR との比較 `C:\MyProj\omr-compare\omr-evaluation-2026-10-26.md` の 4.1・5.3。homr の古いスキャンへの強さは、
   多くの楽譜を複数の書体で描き、augraphy で強く汚した学習から来ている）。規則は記譜の文法による組み立てと検算（小節の長さ、声部、Fixes、Verify）に寄せる。
4. **学習と評価は別の乱数種で分ける。** 学習は seed 1、評価は seed 7。実譜は学習に使わない（評価専用）。
5. **回帰は入れない。** コミットの前に `tools/check.ps1` を実行する。WORSE が出たら、理由を説明できる
   場合に限り `-Update` で受け入れ、HANDOFF にその理由を書く。
6. **速さを保つ。** 1 ページ 1〜2 秒、60 曲の評価を 1 分以内に保つ。

## 3. ワークストリーム

同時にすべてを進めない。各セッションでは 1 本（多くて 2 本）を選ぶ。

### W1 評価基盤（常に最優先で保守する）
- 記号単位の採点（`SvgTruth` / `SymEval`）、音符単位の採点（`Scorer`）、回帰チェック（`check.ps1`）。
- 今後: 採点項目を増やす（連符、声部、調号の変化、タイ・スラー）。誤りごとの切り出し画像を出す。
  「Lily# で描き直して元と比べる」照合。

### W2 データ生成（OmrGen）
- スイート: basic / ledger / tuplets / chords / voices2 / piano（ほかに名前で頼むもの: band、lied = 歌 + ピアノで、休む歌の譜表を隠す）。
- 今後: 記譜要素を増やす（タイ、スラー、強弱、装飾音、反復、歌詞、多段組のパート譜）。
  画質の揺らぎ（解像度、にじみ、傾き、スキャンのノイズ）。別フォント（M2、Lily# 側の対応が必要）。

### W3 記号の認識
- 五線、小節線、符頭、符幹、連桁、付点、臨時記号、休符、音部記号、調号、拍子、連符。
- 今後: 学習した分類器（`GlyphKnn`）の対象を広げる（拍子の数字、音部記号、C 記号）。
  符頭の検出も学習ベースに移す（M4 への布石）。

### W4 組み立てと全体推論
- 和音、声部、音価、小節の割り付け、`.lys` の出力。
- 今後: **仮説と制約による選択**。各記号の候補を確信度付きで残し、次の制約で組み合わせを選ぶ。
  - 小節の長さの合計
  - 全パートの拍子が一致すること
  - 調号の並び順
  - 声部の整合
- 声部の分離の精度（chords の inVoice が低い）。

### W5 一般化（M2）
- 別フォントと別の組版ソフトに対応する。
  - 各楽譜で確信の高い記号から形を学び直す（楽譜ごとの校正）
  - 学習データのフォントを増やす
- 実譜のベンチマークを増やす。MuseScore の元ファイルがあれば、MusicXML から正解を作れる。

### W6 記譜の範囲（M3）
- タイ、スラー、アーティキュレーション、強弱、テンポ表示、装飾音、反復記号、歌詞、テキスト。
- W2 で生成し、W1 で採点を作り、W3/W4 で読む、の順で 1 要素ずつ進める。

**2026-10-26 オーナーの方針: 近い将来、Lily# OMR を Apache-2.0 でオープンソースにする**（有償化の利益は小さく、公開の利点の方が大きい）。
以下の有償化・ログイン・料金の検討は経緯として残す。これからは「Apache-2.0 で配れるか」を依存・データ・モデルの判断基準にする:

### ライセンスの構造

### Lily# 連携と収益化の方針（2026-10-04、ユーザーと相談した案。決定ではない）

**前提**: Audiveris（AGPL、無料、ローカルで動く）と同じページで比べると、開発に使っていない評価台でこの OMR 89.2%・Audiveris 83.8%（HANDOFF）。
精度だけで有料の差をつけるのは難しい。ただし PhotoScore などは無料の Audiveris がある中で売れ続けている = 利用者は修正の使いやすさ・手軽さ・連携に払う。

**ユーザーの狙い: OMR を Lily# の入口にする。** 新しい楽譜ツールに移る最大の壁は手持ちの楽譜の打ち直し。OMR が紙・PDF の楽譜を数秒で `.lys` にすれば、
テキストなので AI に移調・編曲を頼める（MusicXML を出す Audiveris にはない流れ）。入口にすることと収益化は両立させる: 入口は無料で広く、たくさん使う人・仕事で使う人から取る。

**連携の機能（案）**
- VS Code のメニュー・エクスプローラーの右クリック・画像や PDF のドラッグ＆ドロップ・クリップボードの貼り付けから読み、読んだ `.lys` をすぐ開く。
- 元の画像に記号単位の確信度を色で描いた注釈画像を開く（今の `verify-pNN.png` を広げる）。
- 自信のない記号に `@todo(#キー, "メモ")` を付け（コンパイルで警告、プレビューで赤）、キーで横の JSON（候補、元の画像の場所）と結ぶ。SyncTeX のように双方向に飛ぶ
  （`@todo` の記号は記号単位、ほかは小節単位）。
- 怪しい場所を VS Code の「問題」に出し、クイックフィックスで次の候補（例: F♯ / F♮ / 付点なし）を示す（S11 の候補と確信度を見せる。今の `// ? verify` の発展）。
- 元の画像・描き直した楽譜・差分を並べて見る。直すたびに描き直しと照合が走る（S12）。
- 範囲を選んで小節だけ読み直す。確信度つきの `.lys` を AI に渡し、音楽的に不自然な場所を指摘させる。
- 利用者の修正を（同意を取って）その楽譜の校正（S4）や将来の学習データに使う。

**ログイン（2026-10-05 ユーザー決定: 有料プランから）**: 無料のベータ（P1）はログインなし。利用の数は利用者が同意したときだけ匿名で数える（VS Code のテレメトリーの設定に従う）。
ログインは有料プラン（P2）を入れるとき、有料の機能にだけ求める（VS Code の拡張機能の GitHub・Microsoft のサインイン）。読み取りはいつもローカル（画像は送らない）。
前の案（最初から必須）は、入口での離脱・P1 からのサーバーの運用・GPL の利用者の反発を避けて採らなかった。
ユーザーは将来、収益化のためにログインを必須にしたい考え（2026-10-05）。そのときも**オフラインで動く形**にする（将来の形、まだ作らない）:
- ログイン（オンライン）でサーバーが**署名つきの利用券**（利用者、プラン、ページ数の枠、期限 = 例 30 日）を出す。OMR は埋めた公開鍵で署名と期限を確かめるだけで、オフラインで動く。
  拡張機能はオンラインのときに裏で取り直して期限を延ばす。ページ数はオフラインの間は手元で数え、つながったら送る。
- **確かめるのは OMR の exe の中**（拡張機能は GPL でソースが公開され、確かめを消せる）。それでも外せる前提で、時計の巻き戻しは最後に見た時刻を覚える程度にとどめる。
- ずっとオフラインの環境（図書館、企業の閉じたネットワーク）には、別の端末でライセンスファイルを発行して持ち込む「オフラインの有効化」を法人のプラン（P3）で。

**配布は 2026-10-12 のオーナー決定で置き換わった**: 無償の Beta として、Lily# とは別の VS Code 拡張（`yotsuda.lilysharp-omr` 案、win32-x64 だけ、`"preview": true`）で出す。
Marketplace がダウンロード・検査・更新を持つので、下の manifest・署名・初回 DL・更新確認は作らない（`docs/repro/lilysharp-handoff-2026-10-12.md`、器は `extension/` と `tools/pack-extension.ps1`）。下は経緯の記録。

**配布（2026-10-05 ユーザーと相談した方向）**: OMR は Lily# に同梱せず、Lily# の拡張機能がメニューから初めて読むときに、同意を取って取ってくる。
GPL の「集積」として同梱も可能だが、OS ごとの大きさ・更新の周期・閉じた部品が入る見え方を避ける。
- OMR 側: 利用者向けの入口（`omr read <画像|PDF>... --out <dir> [--lysc <path>] [--progress json]`、`omr --version --json`、終了コード、stdout に進み具合の JSON の行）、
  OS ごとの zip（`dotnet publish -r <rid>`。win-x64 で ONNX Runtime 11 MB + モデル 4.7 MB）、公開の置き場所の一覧 `omr-manifest.json`（版、OS ごとの URL と sha256、取り決めの版 `protocol`、必要な Lily# の最低の版）。
  lysc は `--lysc`、無ければ自分の隣、無ければ PATH の順で探す。
- Lily# 側: 一覧から対応する `protocol` の範囲で自分の OS の最新を選び、同意を取って `globalStorageUri` に取り、sha256 を確かめて展開し、`omr --version --json` で確かめてから子プロセスで呼ぶ。起動時に更新を確かめる。
- リポジトリは private のまま（`data/scans` の市販のスキャン、有料プラン）。配布物と一覧は公開の場所（バイナリだけの公開のリリース用リポジトリ、または静的ホスティング）に置く。
  一覧は署名する（公開鍵を拡張機能に埋める）。exe はコード署名（Authenticode、mac は notarization）。self-contained か NativeAOT で発行（NativeAOT と ONNX Runtime は要確認）。
  zip に ONNX Runtime（MIT）の表示。Remote（WSL・SSH）ではリモートの OS 向けを取る。
  OMR の場所は**設定画面に出さない**（2026-10-05 ユーザーの意向）: 普段は拡張機能が置いた場所、開発は環境変数（例 `LILYSHARP_OMR_PATH`、F5 なら `launch.json` の `env`）、
  オフラインはコマンド「Install OMR from File…」（同じ署名・ハッシュの確かめをして同じ場所に置く）。
  ~~公開の配布の前に、学習データのフォント（Emmentaler、MuseScore の Finale Maestro・Finale Broadway など）のライセンスとモデルへの及び方を確かめる。~~ 2026-10-17 確認済み（上）。
- **解析への備え（2026-10-05 ユーザーと相談）**: 配布物は逆アセンブルされる前提。互換の OMR は呼び出しの取り決め（GPL の拡張機能から読める）だけで作れ、止められない。
  取られうるのは検出器のモデル（どの言語でも ONNX のファイルは取り出せる）と読み取りの規則のコード。一番の資産（学習データの工場、正解の作り方、評価台）は配布物の外にある。
  **C++ への書き直しはしない**（モデルは守れず、C++ も解析でき、約 9,000 行の移し替えで数か月と回帰の調査がかかる）。配るときは **NativeAOT** で発行する（IL が残らず C++ 並みに読みにくい。
  .NET の実行環境も要らない）。System.Drawing と ONNX Runtime が AOT で動くかは要確認（System.Drawing を置き換えるときは AOT で動くものを選ぶ）。足りなければ難読化と、利用規約で解析・再配布を禁じる。
  守りの中心は精度・更新・使いやすさ・コピーしにくい有料の価値（法人の一括処理、API、サポート）。
- ONNX Runtime（MIT、全 OS 対応）は残す。全 OS で動かすのに外すべき依存は System.Drawing（`net10.0-windows`）。置き換えは §5 の判断（SkiaSharp は「今はしない」のまま）。

## 7. セッションの進め方

1. `docs/ROADMAP.md` と `docs/HANDOFF.md` を読む。`docs/repro/REQUESTS.md` に Lily# 側が `fixed` にした項目があれば、新しい lysc で確かめて `done` にする（絵が変わる直しなら生成譜の台を描き直す）。
2. `pwsh tools/check.ps1` を実行し、基準値と一致することを確かめる（ずれていたら、まずその原因を調べる）。
   背景で走らせるなら `cmd /d /s /c "pwsh -File tools\check.ps1 < NUL > log 2>&1"`。**2 つ同時に走らせない**（同じ `out/` に書いて偽の WORSE が出る）。
3. HANDOFF の「次の一手」から始める。対象の誤りを `out/gen/**/omr/sym-diffs.txt` で確認し、
   画像を切り出して目で見る。
4. 直したら `tools/check.ps1` を実行する。改善を確かめてから `-Update` で基準値を更新し、コミットする。
   **検出器を学習し直したとき**は、採る前に実譜の評価台（`tools/run-audiveris.ps1 -Eval -Reuse`、6 分）も回し、全体と台ごとの数字を HANDOFF の最新の記録と比べる。
   生成譜の「学習の揺れ」の WORSE を受け入れる前に、実譜で下がっていないことを確かめる（2026-10-20: detector26 で 39-1 の scan が 91.5 → 89.2 に下がり、4 日気づかなかった）。
   **効き目は対照と比べる**（2026-10-27: 前と同じ作りで学習し直すだけで開発用の台が −293。規則が今のモデルの得点に合わせてあるため。対照は `tools/train-model/detector34c.onnx` = 33b の作り、要るなら今のモデルの作りで作り直す）。
   評価台の画像で読み手をデバッグはしない（下がった台は、どのコミット・どのモデルからかを古い版で読み比べて決めるところまで）。
   評価台・開発用の台を回すと台ごとの数字が `docs/eval-sets.tsv`・`docs/dev-sets.tsv` と比べて出る（better / WORSE）。採るなら `out/audiveris/<kind>-sets.tsv` を `docs/` に写してコミットする。
5. 終わりに HANDOFF を書き換え（現在地、数字、次の一手、未解決の疑問）、コミットする。
6. 完了報告の末尾に、**次の一手をこのセッションで続ける方が有利か、コンテキストをクリアして新しいセッションで始める方が有利か**の
   判断を理由つきで書く（目安: 今のコードの文脈が要る小さな仕上げは続ける。学習し直しや新しい領域の読み込みが要る大きな一手は
   新しいセッションで、HANDOFF を計画にして始める）。
