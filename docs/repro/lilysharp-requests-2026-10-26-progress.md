# Lily# から OMR へ（2026-10-26・お願い: 読みの段を `stage` で知らせてほしい／五線の無い頁の下見が遅い）

オーナーの声: 「OMR の処理が遅い。これは仕方がないけど、もう少し詳細な進捗を表示してほしい」。Lily# の側は今日、通知に**段・頁・経過時間・残りの目安**を毎秒出すようにした（Lily# の未 push の commit・`ReadProgress`）。ただ、いちばん長い区間で OMR から何も届かないので、そこは経過時間しか言えない。

拡張と同じ引数（`read … --progress json --verify --lysc …`）で、stdout／stderr の各行に経過秒を付けた（Lab `sessions/p977/omr-timing.txt`）。

## お願い 1: 段を `stage` イベントで（任意の欄・protocol 1 のまま）

```json
{"event":"stage","stage":"layout","page":2,"of":6}   // 頁 2 の下見を始める（GuessLayout の各頁の頭）
{"event":"stage","stage":"read"}                     // 読みの本体を始める（最初の頁の Reader.Read の前）
{"event":"stage","stage":"verify"}                   // 照合を始める（verify.Compare の前）
{"event":"stage","stage":"write"}                    // 書き出しを始める（Finish の頭）
```

- Lily# はもう受ける（`parseEvent` の `stage`・`ReadProgress`）。知らない `stage` の名前は無視する＝段を足すのは自由。`page`／`of` は任意。
- `layout` の頁の頭が来れば、Lily# は「finding the staves: page 2 of 6… 0:25 (about 0:56 to go for the staves)」と言え、通知の棒も 0〜40% を進められる。今は 11 分のあいだ 0% のまま。
- `read` が来れば、読みの本体の 1 頁目にかかった時間も残りの目安に入る（今は 2 頁目以降の間隔からしか測れない）。

## お願い 2（判断はそちら）: 五線の見つからない頁の下見が、下見の 94% を占める

`--parts-only`（下見だけ）を単独で回した（Lab `sessions/p977/omr-layout-timing.txt`）:

| 頁 | 五線 | 下見の時間 | 中身 |
|---|---|---|---|
| 1（表紙） | 0 | **28 秒** | 検出器を間隔 14〜40 の 7 通りで（14 で 10 秒・17 で 9 秒） |
| 2（ほぼ白紙） | 0 | **142 秒** | 同じく 7 通り。間隔 14 だけで 44 秒・見えた記号は 0〜1 |
| 3・4・5 | 14 | 各 約 2 秒 | 間隔 1 つ |
| 6（最後） | 0 | **19 秒** | 7 通り |

計 202 秒のうち **189 秒が五線の無い 3 頁**。`ReadCommand.GuessLayout` の `wide.Count == 0` の枝（「a second a go」の想定）が、413 dpi の頁で 1 回 1〜44 秒になっている。白紙に近い頁ほど遅いのは意外（記号が無いのに 2 頁目が最も遅い）。

直し方の案（どれを採るかはそちら）: インクの少ない頁は検出器を回さずに「五線なし」とする／間隔の掃きで何も見えなければ打ち切る／下見の解像度を落とす。（読みの本体では同じ 3 頁が 0.9・1.8・4.4 秒で済んでいる＝遅いのは下見だけ）

返事は不要（1 を入れたら版と一緒に知らせてほしい。Lily# の側は何もしなくても効く）。
