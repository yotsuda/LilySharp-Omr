# Lily# への提案（2026-10-04、OMR と Lily# の連携のために）

ROADMAP §6「Lily# 連携と収益化の方針」の Lily# 側の分。狙いは **OMR を Lily# の入口にする**こと: 紙・PDF の楽譜を数秒で `.lys` にし、
VS Code の中で、元の画像と見比べながら、OMR が自信のない所だけを直せるようにする。Lily# の改善は別のセッションで進めるので、そちらへの依頼をここにまとめる。

## 前提（守ること）

- **OMR は別プログラムのまま。** Lily#（拡張機能・lysc・LSP）は OMR を子プロセスとして呼び、OMR が書いたファイル（`.lys`、JSON、PNG）を読むだけ。
  OMR のコードを Lily# に入れない、Lily# のコードを OMR に入れない（ROADMAP §6 のライセンスの分離）。
- **確信度の数字は `.lys` の文法に入れない。** `.lys` に書くのは、人が読んで分かる **`@todo`（未解決の印とメモ）だけ**（下の A1）。`@todo` は OMR 専用ではなく、
  作曲・編曲で「あとで確かめる」所に誰でも使える汎用の機能にする。確信度の数字・候補・元の画像の座標は横に置く JSON（D）に入れ、`@todo` のキーで結ぶ。
- 今ある仕組みを使う: プレビューの `data-pos` によるクリックで飛ぶ機能、`lilysharp.importMusicXml`（取り込みのコマンドの先例）、AI 変換（`docs/ai-collab-design.md`）の `checkCandidate`/`renderText`。

## A. 言語（`.lys`）

### A1. 未解決の印 `@todo` — **要判断（ユーザー案 2026-10-04）**

音符・休符・和音の後ろに付ける「あとで確かめる」印とメモ。OMR は自信のない記号にだけ付ける。

```
c'4 fis'8@todo(#o1203, "F♯ か F♮（臨時記号がかすれている）") e'8 [e' g']4 |
r2@todo("小節 12: 長さが 7/8 しかない") d'2 |
c'4@todo e'4 g'2 |
```

- 形は `@todo`、`@todo("メモ")`、`@todo(#キー, "メモ")`。既存の注釈（`@hammerOn`、`@bend(full)`、`@chord(…)`）と同じ並び。
- **`#キー`**（任意）は横の JSON（D）の候補・確信度・元の画像の場所と結ぶための名前。人は書かなくてよい（手で付ける `@todo` はメモだけで足りる）。
  `#` は `@chord(F#m)` で使われているので、字句の扱いは Lily# 側で確かめる（だめなら `@todo(o1203: "メモ")` などに変える）。
- 小節全体のこと（長さが合わない、など）は、その小節の最初の音符・休符に付ける。
- **描画にも再生にも効かない。** 印刷（`lysc png`/`pdf`/`svg`）には出さない。
- **コンパイルで警告**: `LYSxxxx: TODO: F♯ か F♮…`（メモの無いものは `TODO`）。VS Code の「問題」に出る。
  `lysc check` の終了コードは変えない（警告のまま）。出版前に残りを止めたい人のために `--todo-as-error`、数だけ見たいときの `--no-todo`（警告を出さない）があると良い。
- **プレビューでは赤く**: `@todo` の付いた符頭・休符・和音を赤で描き、マウスを乗せるとメモを出す。プレビューの設定で赤を消せる。
- 整形・オクターブの変換・`extractPhrase`・AI 変換などの書き換えで**消さずに運ぶ**（AI 変換は選んだ範囲の `@todo` を、直した所は外し、直していない所は保つよう `GRAMMAR_FOR_LLM.md` に書く）。
- SVG に `data-todo="o1203"`（キーが無ければ空）として出す（C2）。

あわせてほしいもの:
- **クイックフィックス「解決済みにする」**（`@todo(…)` を消す）。直した音符の上で 1 回で外せる。範囲・ファイル全体の一括もコマンドで。
- 構文の色分けで `@todo` を目立たせる（コメントの TODO と同じ扱い）。
- 「問題」とは別に、ファイルの `@todo` の一覧（アウトラインやコマンド「次の TODO へ」）。

ほかの案と比べた理由:

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`@todo` を文法に足す（推奨）** | 人が読んで意味が分かる。書き換えに強い（音符にくっついて動く）。OMR 以外にも使える（作曲中のメモ、レビュー、AI の作業の印）。直したら外すだけで、残りの数が進み具合になる | 文法が 1 つ増える |
| 意味のない札 `@id(o1203)` を全部の音符に（前の版の案） | 全部の音符を元の画像と結べる | 人には意味が分からず、使い道が無い。`.lys` が読みにくくなる |
| コメントに書く（`// TODO: 小節 12 …` を行末に） | 文法を変えない | 行の中のどの音符か分からない。書き換えでずれる。プレビューで赤くできない |

`@todo` は自信のない記号にだけ付くので、**元の画像との行き来（B3）は、`@todo` の付いた音符は記号単位、それ以外は小節単位**（D の `measures`）になる。
全部の音符を記号単位で結ぶ必要が出たら、そのとき別に考える。

### A2. 元の画像を指す見出し — 小（任意）

`.lys` から、OMR の横のファイル（D）を見つけられるように。文法を足すなら、メタデータの並びに 1 行:

```
omrSource "scan.omr.json"
```

足さない場合は「`x.lys` の隣の `x.omr.json`」という名前の約束だけで足りる（**推奨: まず名前の約束で始め、要れば文法にする**）。

## B. VS Code の拡張機能

| # | 機能 | 中身 | 大きさの見立て |
|---|---|---|---|
| B1 | **画像・PDF からの取り込み** | コマンド「Lily#: Import from Image/PDF…」（`importMusicXml` と同じ並び）。エクスプローラーの右クリック（`.png` `.jpg` `.tif` `.pdf`）、エディターへのドラッグ＆ドロップ、クリップボードの画像の貼り付けからも。設定 `lilysharp.omr.path` の OMR を子プロセスで呼び、進み具合を通知に出し、終わったら `.lys` とプレビューと注釈画像を開く。OMR が無ければ設定を案内する | 小〜中 |
| B2 | **`@todo` の候補をクイックフィックスに** | 「問題」に出すのは A1 の警告（コンパイラーの仕事）。拡張機能は、`#キー` の付いた `@todo` に、`x.omr.json` の候補を**クイックフィックスとして足す**（`candidates[].text` で音符を置き換え、同時に `@todo` を外す。例: `fis'8` / `f'8` / `f'8.`）。候補が無いものは「解決済みにする」だけ | 小〜中 |
| B3 | **元の画像のビュー（SyncTeX のように）** | Webview に元のページ画像を出し、`@todo` の記号の枠を赤で描く。枠のクリック → `.lys` のその `@todo` へ。`.lys` のカーソル → `@todo` の上なら記号の枠、ほかは小節の枠を光らせ、そこへスクロール（D の `measures`）。プレビューのクリックでも同じ | 中 |
| B4 | **見比べのビュー** | 元のページと Lily# の描き直しを並べ、小節を揃えてスクロール。OMR の照合（`--verify`）が出す食い違いの小節を両方に枠で出す。描き直しは既存のプレビュー | 中〜大 |
| B5 | **保存で照合をやり直す** | 保存したら OMR を `--verify` で呼び直し、B2 の診断と B4 の枠を更新する（任意の設定。数秒かかる） | 小（B2・B4 の後） |
| B6 | **AI 変換に読み取りの情報を渡す** | `ContextBuilder` に、選んだ範囲の `@todo` のメモと、JSON の確信度・候補を足す。例: 「怪しい所を直して」で、AI が候補から音楽的に自然なものを選ぶ。採るかどうかは今どおり描いた譜面で決める | 小 |

B3・B4 は、OMR が出す座標（D の `box`）と、Lily# の SVG の `data-todo` と小節の位置（C2）があれば作れる。

## D. OMR と Lily# の取り決め（横のファイル）

OMR が書き、Lily# は読むだけ。`x.lys` の隣に置く。形は最初の版として OMR 側で決め、Lily# の都合で変えてよい（`version` を見る）。

```json
{
  "version": 1,
  "omr": "LilySharp-Omr 0.x",
  "pages": [ { "page": 1, "image": "scan-p01.png", "width": 2480, "height": 3508, "annotated": "scan.omr-p01.png" } ],
  "measures": [ { "measure": 12, "part": 1, "page": 1, "box": [790, 400, 1120, 520] } ],
  "todos": [
    { "key": "o1203", "page": 1, "box": [812, 440, 840, 468], "kind": "note", "measure": 12, "part": 1,
      "confidence": 0.62,
      "candidates": [ { "label": "F♯", "text": "fis'8" }, { "label": "F♮", "text": "f'8" } ] }
  ]
}
```

**OMR 側の実装（第 1 版、2026-10-04）**: OmrProto は `omr.lys` の隣に毎回 `omr.omr.json` を書く。今入っているのは次のとおりで、上の案より少ない。
```json
{ "version": 1, "omr": "LilySharp-Omr OmrProto", "lys": "omr.lys",
  "pages": [ { "page": 1, "image": "C:\\…\\p01.png", "width": 2480, "height": 3508 } ],
  "measures": [ { "measure": 4, "part": "lh", "line": 33, "page": 1, "box": [1292, 1046, 2223, 1203] } ],
  "todos": [ { "key": "b4-lh", "kind": "bar", "source": "verify", "measure": 4, "part": "lh", "lines": [33],
               "page": 1, "box": [1292, 1046, 2223, 1203], "memo": "bar 4: voices 600+1880/2400 ticks", "candidates": [] } ] }
```
- `measures` はパートごと・小節ごとに 1 つ。`line` はその小節を書いた `omr.lys` の行（1 から）。`part` は `.score` のパートの名前。
- `todos` は今は**小節単位だけ**（`kind: "bar"`）: 照合（`--verify`）の警告、照合なしなら小節の長さが合わないもの。`part` が `null` の todo は段全体（符幹・連符の数字の食い違い）で、`lines` はその小節の全パートの行。
  記号単位の todo（自信のない音符）と `candidates` はまだ無い（読み取りの結果に記号ごとの確信度を運ぶのが次の仕事）。
- `box` は**読み込んだままの画像**の画素（OMR が内部で傾きと反りを直した座標を元に戻してある）。
- `.lys` にはまだ `@todo` を書かない（Lily# が読めるようになってから）。今は `// ? verify bar N: …` のコメントのまま。

- `box` は元の画像の画素。`key` は `.lys` の `@todo(#o1203, …)` のキー。`text` は、その `@todo` の付いた字句（音符・和音・休符の 1 つ）を置き換える `.lys` の文字列（`@todo` を除く）。
- `measures` は全部の小節の場所（B3・B4 の小節単位の行き来）。
- どの確信度から `@todo` を付けるかは OMR 側の設定（`.lys` に書く前に決まる）。
- OMR はこれまで `omr.lys` に `// ? verify bar N: …` を、`verify-pNN.png` に赤枠を出している。A1 が入ったら `@todo("小節 N: …")` に移す。

## E. ライセンスの注意

すべて「Lily# が子プロセスを呼び、ファイルを読む」形なので、OMR と Lily# の分離は変わらない。拡張機能に OMR を同梱するかどうか（別にダウンロードさせるか）は、
OMR の配り方（ROADMAP §6 のログイン・無料枠）の判断と一緒に決める。それまでは設定でパスを指す。
