# Lily# から OMR へ（2026-10-29）: 直した小節を種に、似た楽譜を作って学習する

> **念押し（オーナーの指示）: OMR fix で Accept した内容は、そのまま学習に使わないこと。**
> 実スキャンの画像と、Accept した `.lys` の組を、検出器の学習データ（正解・擬似正解・`pseudo.py` の頁・重みつきのサンプルなど、形を問わず）にしてはいけない。Accept は試しに押されることがあり、正しいとは限らない。学習に入るのは、種から**生成した**楽譜（lysc が描いた画像と、その SVG の正解）だけ。実スキャンの小節は評価にだけ使う（下の 4）。
>
> **念押し 2（オーナーの指示）: この仕組みは OMR のリリースにも Lily# のリリースにも同梱しないこと。**
> 種の置き場（スキャン・直した `.lys`）、種から作った楽譜、種を読む道具、評価の台に足した実スキャンの小節は、オーナーの機械の中だけのもの。Scan Import 拡張・`omr.exe`・README・サイトのどこにも入れない。リリースに入るのは学習し直した `detector.onnx` だけ。詳しくは下の「リリースに入れない」。

## きっかけ（オーナーとの話、2026-10-29）

Lily# のセッションで「OMR fix のために手元の LLM を作れるか」を話した結果、手元の LLM より OMR 本体を育てるほうがよい、となった。その中でオーナーが決めたこと:

- **OMR fix で直した小節を、そのまま学習の正解にはしない。** 理由は 2 つ。
  1. 直した `.lys` は小節の中身しか言わず、スキャンのどこに何があるか（検出器の枠）は言わない。知りたいのは検出器が見落とした記号の位置で、それは検出器にも分からない。
  2. 間違って Accept したものが、そのまま誤りとして学習される。そうなると、オーナーが OMR fix を気軽に試せなくなる。
- **ほかの利用者から集めることもしない**（同意・楽譜の著作権・受け口が要る。利用者が増えてから考える）。
- 代わりに、**オーナーが「この小節を間違えた」と伝えた小節を種にして、似た楽譜を生成器で大量に作り、学習に使う。** 種が少し違っていても、Lily# がその `.lys` どおりに描くので、生成した楽譜の画像と正解はいつも一致する。間違った Accept でも学習は汚れない。
- 種にするのは**オーナーが伝えた小節だけ**。Accept のたびに自動で集めることはしない。

1 回の気づきを何千もの学習例にする、という点では、S14 以降で新しい記号を足してきたやり方（生成器 → SVG 正解 → 検出器 → 読み取り）と同じ。違うのは、出発点が「記号の種類」ではなく「実際に読み違えた 1 小節」であること。

## お願い

形や名前はそちらで決めてほしい。以下は Lily# 側から見た一案。

### 1. 伝え方（オーナー → OMR）

オーナーが渡すもの:

- スキャン（PDF か画像）と、その読みの `.lys`（OMR fix で直した後のもの = 正しい中身）
- 間違えた小節（パートと小節番号。例: 「right の 12・13 小節」）
- 分かれば、何が違ったか（「♮ が抜けた」など）。無くてもよい

置き場の決まり（例: `data/seeds/<日付>-<曲>/` に 3 つ置いて 1 行の `seed.json`）を決めてもらえれば、オーナーはそこに置いて「種を置いた」と言うだけにできる。

### 2. 切り分け

まず、その小節で何が起きたかを分ける（`--verify` や `--export-read` と、直した `.lys` を比べる）。

- **検出器が見落とした・見間違えた** → 3 へ
- **見えていたのに `.lys` への直し方が違う** → 読み取りの規則を直す。学習は要らない
- **まだ扱っていない記号** → これまでどおり S 番号の段階を 1 つ足す

### 3. 種から似た楽譜を作る（検出器の分）

その小節（と、拍子・調・音部記号・パートの宣言）を種に、生成器で変化をつける:

- **中身**: 移調、リズムや和音の形を少し変える、前後の小節を同じ曲の別の小節や生成した小節に差し替える。ただし、読み違えの原因になった組み合わせ（例: 背の高い低音の和音の ♮、古い刷りの「z」形の休符）は残す
- **見た目**: 書体・五線の大きさ・段の詰め方を変え、`degrade.py` で元のスキャンに近い汚れ（かすれ・太り・ゴミ・裏写りなど）をかける

正解はこれまでどおり lysc の SVG から取る。

### 4. 確かめる

- 学習し直したら、いつもの check（better / WORSE）で、ほかの台が悪くなっていないかを見る
- **実際に読み違えたその小節は、学習には使わず評価に使う**: 種にした実スキャンの小節を開発用の台（例: `real-fixes`）に足し、学習し直した後にその小節が直した `.lys` どおりに読めるかを見る。ここなら枠は要らない（小節の中身を比べるだけ）。オーナーが Accept を間違えていた場合は、ここで食い違いとして見えるので、オーナーに確かめる

## リリースに入れない（オーナーの指示）

この仕組みは**オーナーの機械の中だけのもの**。OMR（Scan Import 拡張・`omr.exe`・Marketplace の README・サイトの文面）のリリースに同梱しないこと:

- 種の置き場（スキャン・直した `.lys`・`seed.json`）と、そこから作った楽譜・学習の窓
- 種を読む道具（切り分け・種から楽譜を作るスクリプト・生成器の種の入口）。生成器や学習の道具がもともと同梱されていないなら、それに入るだけでよい
- 評価の台に足した実スキャンの小節（オーナーのスキャン。著作権が残る曲もある）

同梱されるのは、学習し直した検出器（`detector.onnx`）だけ。リリースの手順や `.vscodeignore` に確かめる行があるなら、そこに `seed` を足してほしい。

Lily# 側も同じ: Lily# の `docs/RELEASING.md` の「4. Verify locally」に、この仕組みのために Lily# が足すもの（種を置く操作など）は Lily# のリリースに入れない、と書いた。

## Lily# 側（追記 2026-10-29: 入れた）

オーナーの要望で、Lily# 側に**報告の操作を先に作った**（Accept とは別のボタン。Accept は今までどおり気軽に押せる）。1 の「伝え方」の置き場の形は、ひとまずこちらで決めた。合わなければ言ってほしい、合わせる。

- **出し方**: オーナーの settings.json に手で `"lilysharp.omr.seedFolder": "<フォルダー>"` を書いたときだけ、Bar fixes パネル（Edit Bars Beside the Scan / Fix OMR Marks with AI）の各小節に **Report Misread to OMR…** が出る。設定は package.json に載せていない（設定画面にも出ない）。他の人には見えない。
- **置き場**: オーナーの機械では **`C:\MyProj\omr-seeds`**（2026-10-29 に設定した）。どのリポジトリの外にも置いたので、コミットにもリリースにも紛れ込まない。
- **押すと**: 正しい小節は**いつもパネルの Draft**（オーナー決定 2026-10-29: パネルで直したテキストが常に報告の対象。ファイルの小節を選ぶ選択肢はやめた）。「何が違った？」を一言聞く。Draft に直しがあるときは空でよい。Draft がファイルと同じ（直していない）ときは必須で、正しい小節の代わりに、何が違うか（どうあるべきか）をオーナーの言葉で書く（このとき `correct` と `fixedCopy` は `null`、`correctFrom` は `none`。種にする前に、そちらで正しい小節を書き起こす必要がある）。そのうえで種のフォルダーの下に 1 件 1 フォルダーを作る。名前は `<日時>-<.lys の名前>-bar<小節>-<パート>`（例 `20261029-153012-largo-bar12-right`）。中身は次のとおり。
  - `seed.json`
  - `.lys` の写し（報告の時点のもの）
  - Draft に直しがあるときは、その小節を Draft に差し替えた `.lys` の写し `<名前>.fixed.lys`
  - side file の写し
  - ページ画像の写し `page-<N>.<拡張子>`
  - 小節の切り抜き `bar.png`
- **1 件のフォルダーだけで完結している**: 材料は Lily# が報告の時点ですべて写す。正しい小節は `correct`、正しい小節の入った楽譜全体は `fixedCopy`。`lysWas` は出どころの記録（元の `.lys` はその後で直されたり消されたりしていることがある）。
- **`seed.json`** の例:

```json
{
  "seed": 1,
  "reported": "2026-10-29T06:30:12.000Z",
  "note": "the natural on the low chord is missing",
  "lysWas": "C:\\scores\\largo.lys",
  "lysCopy": "largo.lys",
  "fixedCopy": "largo.fixed.lys",
  "measure": 12,
  "part": "right",
  "line": 40,
  "bar": "<a b d'>4 ... |",
  "correct": "<a b dis'>4 ... |",
  "barWhenOpened": "<a b d'>4 ... |",
  "editedSinceOpened": false,
  "correctFrom": "draft",
  "falseAlarm": false,
  "partial": false,
  "scan": {
    "page": 2, "box": [x0, y0, x1, y1],
    "image": "C:\\scores\\largo-2.png", "imageCopy": "page-2.png", "crop": "bar.png",
    "sideFile": "C:\\scores\\largo.omr.json", "sideFileCopy": "largo.omr.json"
  }
}
```

`bar` は報告の時点のファイルの行（`@todo` も含む）、`correct` は正しい小節（印は外してある）。`correctFrom` は `draft`（パネルの Draft）か `reading`（読みは正しく、`@todo` が誤報＝パネルの「Reading is right — @todo is a false alarm」の箱。`correct` は読み手の小節から印を外したもの、`falseAlarm` は `true`。検出器ではなく照合の誤報の例として使ってほしい）か `none`（Draft に直しが無い。`note` だけが手がかり）。**読み手の生の読み**: `barWhenOpened` はパネルが最初に持っていた小節（パネルを開く前にエディターで直していなければ読み手のもの）、`editedSinceOpened` はその後エディターで変わったか。**`lysCopy` の他の小節は読み手のものとは限らない**: オーナーは小節を Accept してから次を報告するので、同じ楽譜の後の報告の `lysCopy` には、前に報告した小節の Accept した直しが入っている（例: tabi-18 の 4 小節目の報告では 2・3 小節目がもう直してある）。読み手の読みとして使えるのは報告した小節の `barWhenOpened` だけ。楽譜全体の読み手の読みが要るときは、写したページを side file の `omr` の版の読み手で読み直す（side file の `verify` には検出器が見た記号もある）。`partial` が `true` のときは、Draft は一部だけ直したもの（パネルの「Draft not fully fixed」の箱）で、`note` に何がまだ違うかが書いてある＝`correct` をそのまま正解にしないでほしい: 種にするなら `note` を読んで直してから、**実スキャンの評価の台には使わない**（正しく読めても違うと数えてしまう）。`measure` と `part` は side file の小節（読み手の番号）、無ければ楽譜の番号。`box` は side file の枠（todo の枠、無ければ小節の枠）。写せなかったものは欄ごと無い。`scan` は枠が無い小節では `null`。

**この報告は学習の正解ではない**（冒頭の念押し）。種と評価の台にだけ使ってほしい。Lily# のリリースにも入れない: コードは拡張に入っているが、設定を書かない限り何も出ず、何もしない。`docs/RELEASING.md` に書いた。
